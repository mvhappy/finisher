# Sub-project 7D: The Claude Code adapter — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Each task names a **model tier** for its implementer: `opus` for semantics (the protocol mapping, permissions, budgets against a process we do not control, isolation checks, resume and crash paths, attribution, the Windows shell), `sonnet` for plumbing (the fake CLI's script runner, detection, console, data files, e2e, docs). Tasks 0 and 18 are controller-run (they need a person-signed-in CLI and other hosts); Task 13's last step needs the Windows host.

**Goal:** a person can start an agent session on the **user-installed, unmodified Claude Code CLI, signed in by the user with the CLI's own flow**, and it behaves like every other harness. After 7D:
- `agent.session.start {harness: "claudeCode"}` runs `claude -p` in stream-JSON with the control protocol, **inside the session sandbox** (`openSessionSandbox`, 7C), with its own per-session config directory and the sign-in store reached in place (`CLAUDE_SECURESTORAGE_CONFIG_DIR`, 7C Task 11);
- its messages, thinking, tool calls, results and usage become the runtime's `ProviderEvent`s (spec §4.1), so nodes, budgets, the journal and the trace store need nothing new;
- its permission prompts (`can_use_tool`) go through 7B's `permissions.ts` and `provider-requests.ts`: allow, deny, or a `provider` approval a person answers from any device;
- interrupt, steer, crash, resume (`--resume`), the version floor, the capability probe, model discovery, account-change detection and **settings isolation without `--bare`** work and are tested against a fake CLI that speaks the same protocol;
- on Windows the shell is the **brokered shell** of spec §4.5 (or the CLI's own PowerShell tool, Owner question 2).

## Global Constraints

**Code**
- MIT. No GPL/LGPL/AGPL/SSPL/EUPL dependency in shipped code (`pnpm gates`). Claude Code is proprietary and **never bundled, copied, patched or wrapped**: detected on `PATH` or at `agents.claudeCode.path`, run unmodified with documented flags, its built-in authentication neither removed nor restricted (spec §4.5 "Licence and terms").
- **Finisher never opens, reads, copies or transmits anything under `<server-data>/providers/`** (spec §8.6). Sign-in state is learned only from what the CLI reports (`auth status`, the `initialize` response's `account`, `system/init`'s `apiKeySource`). A test spies on file access (Task 11).
- **No cloud-only imports.** **Primitive ops live only in `fin-core`**: 7D adds none. **Model and event types are generated, never hand-written:** 7D adds no `fin-core` event kind; if one is needed (Task 10's account hash in a journal kind), it goes through `export_schema.rs` and the generated-types drift gate. Control-plane schemas (the protocol lines, the probe cache) are Effect Schemas in `apps/finisherd` or `@finisher/contracts`.
- **File sizes:** non-test source ≤ 600 lines, tests ≤ 1,500; `runtime.ts`, `runtime-engine.ts`, `wiring.ts` and `rpc.ts` take call-site lines only.
- Errors are `{code, message, details, fix?}`; any new code goes into `crates/fin/src/output.rs`, `apps/finisherd/src/errors.ts` and `console/exit-codes.ts` (the parity test).

**Testing and process**
- **Real providers never run in CI** (spec §1.3): every test uses `fake-claude` or recorded transcripts; the real CLI runs only in Tasks 0, 13 (Step 0) and 18, on an account a person signed in (Owner question 1).
- Real engine and real `control.db` in tests; the session sandbox in `direct` mode, and in `launcher` mode on Linux with `FIN_TEST_SANDBOX_READY=agent` (test-hooks builds), so `fake-claude` runs under the real launcher.
- **Before each commit, every task runs** `rtk cargo test --workspace`, `rtk pnpm test` and `rtk pnpm gates`; tasks touching the runtime, RPCs or console also run `rtk pnpm e2e`.
- Commits use Conventional Commits, author `mvhappy <333925574+mvhappy@users.noreply.github.com>`, trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Prefix shell commands with `rtk`, after `source .superpowers/env.sh`.
- **The repo is public:** no host names, user names, account e-mails or key names in tracked files; **recorded transcripts are scrubbed** (paths, user and host names, account labels, session ids) and checked by the D-plan's "never raw" grep before commit.
- **Tracker:** each task ticks its line in `TASKS.md` under a new "Sub-project 7D: Claude Code adapter" section, in the same commit.

## Decisions taken here (the spec fixes the shape; these fix the details)

### Launch and isolation

1. **The command line** (`claude/launch.ts`), in this order: `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-mode manual --permission-prompts host --permission-prompt-tool stdio --setting-sources user --settings <agents/<id>/settings/claude.json> --strict-mcp-config --mcp-config <agents/<id>/settings/mcp.json> --tools <allow-set> --disallowedTools <deny-set> --disable-slash-commands --append-system-prompt-file <agents/<id>/settings/role.md> --model <m> --session-id <uuid> | --resume=<uuid>` and, when the session has a money budget and the sign-in is not a plan, `--max-budget-usd <remaining>`. Files, not argv, carry the prompt and settings (no prompt text in `ps`; the Windows command-line limit). `manual` is what `claude --help` lists (docs: `default` is its alias; the fake accepts both). *Rationale:* every flag is documented except `--permission-prompt-tool stdio`, which is absent from `--help` but is the value the Agent SDK passes (`types.py`) and is present in the binary; the probe (Decision 8) proves it per version, and Decision 10's fallback exists if it goes. **`--restricted` is the candidate replacement for `--setting-sources user`** (made for "an evaluation harness [that] drives `claude` on a shared machine": only managed settings and `--settings`, file tools confined to the working directories, Bash only when `--tools` names it): Task 0 checks that it keeps the `--mcp-config` SDK server, the tools `--tools` names and the user's sign-in; if it does, the launch uses it and drops `--setting-sources`. `--safe-mode` is not used (it may drop `--mcp-config` servers). `--system-prompt-snapshot` stays on: a role prompt edited later applies to new sessions only, which matches 7B's versioned prompts. *Task 0 (unsigned, 2.1.321, 2026-11-12)*: every flag above is accepted by 2.1.321 in this order (also `--permission-mode default`, `--model default` and `--model claude-opus-5-5`, `--resume=<uuid>`); `--permission-prompt-tool` and `--append-system-prompt-file` are absent from `--help` (raw help in `archive/7d-task0/`). `--restricted`, alone or with `--setting-sources user`, kept the SDK server, the `--tools` names and `--settings`, and binds no inbox socket (Facts); it is **not** stricter than `--setting-sources user` about the project folder (both still read `.claude/settings*.json`, neither loads them). The switch to `--restricted` waits only on the signed-in check that OAuth still works (Step 3). *Task 0 (signed in, 2.1.321, 2026-11-13)*: `--restricted` keeps the claude.ai sign-in (a signed-in turn ran; `initialize.account` reported the plan), so nothing blocks the switch; the probe's flag stays the selector until Task 4's golden argv adopts it.
2. **`--tools` is an allow-list, replacing the spec's deny-list built from `init.tools` (deviation from §4.5 item 4, recorded in Task 17).** The spec's list was built after the fact from `system/init`, which arrives only with the first prompt (Task 0 fact), so the first turn would already have the new tools. `--tools` names exactly the role's allow-set intersected with the tools Finisher maps (`Read`, `Edit`, `Write`, `Glob`, `Grep`, `Bash` where the OS has it, `WebFetch` and `WebSearch` per the role); a tool a newer CLI adds is absent unless named. `--disallowedTools` lists `Task`, `Agent`, `Workflow`, `SendMessage`, `Skill`, `Cron*`, `ScheduleWakeup`, `Monitor`, `EnterWorktree`, `ExitWorktree`, `AskUserQuestion`, `NotebookEdit` and `ToolSearch` as a second layer. **No `mcp__*` deny:** deny beats allow, so it would also remove Finisher's own `mcp__finisher__*` tools; `--strict-mcp-config` already admits only Finisher's servers. The probe checks `init.tools ⊆ allow-set ∪ Finisher's MCP tools` on every instance (Decision 8). *Task 0 (unsigned, 2.1.321, 2026-11-12)*: `init.tools` was exactly the six named tools plus `mcp__finisher__shell`; the 2.1.321 default set also holds `EnterPlanMode`, `ExitPlanMode`, `ListAgents`, `ReportFindings` and `TaskStop`, so the second-layer list adds them; `Cron*` works as written (a trailing wildcard). A CLI reaches `fin` through its shell, so for `claudeCode` a `fin` in the allow-set enables `Bash` in `--tools` (and its `ask` entry) even when the role does not name `Bash` (critic, colourist, mixer, clip-finder, caption-stylist, fixer); 7B's `permissions.ts` decides each call, and owner Q3(a) keeps it at `ask` while the profile is not enforced (Task 8).
3. **The per-session config directory is `agents/<id>/provider/`** (`CLAUDE_CONFIG_DIR`, 7C), created empty; **the sign-in store is `providers/claudeCode/home/store/`** named by `CLAUDE_SECURESTORAGE_CONFIG_DIR` (7C Task 11, from S9 B7: the CLI refuses a symlinked store and replaces a hard link on refresh). That variable is **undocumented**; Task 0 re-checks it on each OS and the probe (Decision 8) checks `account.tokenSource` per version. If it stops working, sessions on that version are refused `PROVIDER_AUTH {fix: "sign-in cannot be shared on this version"}`; Finisher never copies the store (spec §8.6). *Task 0 (signed in, 2.1.321, 2026-11-13)*: confirmed on Linux: the CLI reads `<store>/.credentials.json` (0600) and, with the variable set, ignores `$CLAUDE_CONFIG_DIR/.credentials.json` (an empty store dir means signed out even beside a signed-in config dir). Not run (no isolated sign-in): `auth login` writing there, a refresh in place under the sandbox, two concurrent refreshes; until Task 18 (or a test-account run) confirms them, Decision 23 assumes `auth login` with both variables writes `.credentials.json` into the store dir and the CLI refreshes it by temp-and-rename **inside that directory**. 7C's `AgentInput.signInStore` grants the store **file** ("never its directory"): if the refresh renames a temp file into place, the file grant cannot cover the temp file, so Task 18 checks a refresh under the launcher before the `agent` profile reaches `READY`.
4. **The session settings file** `settings/claude.json` (read-only to the sandbox, 0600, written by `finisherd` before launch): `{"disableAllHooks": true, "autoMemoryEnabled": false, "crossSessionInbound": "refuse", "attribution": <off>, "cleanupPeriodDays": <retention>, "permissions": {"defaultMode": "default", "blockWritesOutsideWorkingDirectories": true, "ask": [<every tool in --tools>, "mcp__finisher__shell"]}, "env": {}}`. **No `deny`/`allow` path rules** (deny beats allow, so a global deny with a workspace allow would block every edit; and a single-`/` path is relative to the settings file). The working directory is the workspace only (no `--add-dir`, Decision 7), so `blockWritesOutsideWorkingDirectories` keeps the CLI's own file tools inside it. **The `ask` list makes every call of every enabled tool a `can_use_tool` request** (docs: an ask rule is how to require a prompt for the auto-allowed reads and read-only commands), so 7B's `permissions.ts` sees and records each one (Decision 18). Keys the CLI does not know are dropped with a probe warning (`claude doctor` is never run: it reads the working directory's settings without a trust prompt). *Task 0 (unsigned, 2.1.321, 2026-11-12)*: **one wrongly typed known key makes `-p` drop the whole file silently** (Facts), which would turn `disableAllHooks` and the `ask` list off without a sign. So Task 4 writes the file from a typed schema, and the probe's step 2 (Decision 8) runs with the same body plus a canary `"outputStyle": "Explanatory"` and requires `init.output_style == "Explanatory"` (an applied file); sessions run without the canary. `attribution: {"commit": "", "pr": ""}` validated. `crossSessionInbound: "refuse"` is a known key (an unknown value is dropped alone) but does not stop the inbox socket being bound (Facts); under `--restricted` no socket is bound. These rules are a convenience layer (spec §7.1 layer 5): 7B's `permissions.ts` and the sandbox decide.
5. **The extra environment** (passed to `spawn` as `SpawnOptions.env`, Task 3b, and admitted through `assertSessionEnv`'s `extra`): `CLAUDE_CODE_TMPDIR=<agents/<id>/tmp>` (S9: without it the CLI exits `EPERM` on `/tmp/claude-<uid>` on macOS), `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, **`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`** (no turn the CLI starts by itself after a `result`: background Bash, background subagents and Monitor watches would otherwise start one, docs "Background tasks at exit"), `BASH_DEFAULT_TIMEOUT_MS=120000`, and on Windows `CLAUDE_CODE_GIT_BASH_PATH` is never set (Decision 21). `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` and every `*_API_KEY` stay in `NEVER_IN_SESSION`. Nothing sets `CLAUDE_CODE_ENTRYPOINT` (Finisher is not the SDK). *Task 0 (unsigned, 2.1.321, 2026-11-12)*: with this environment (and `HOME`, `CLAUDE_CONFIG_DIR` redirected, nothing else set) `initialize.account.tokenSource` was `none` in every run; `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` kept every `CLAUDE.md`/`CLAUDE.local.md`/`AGENTS.md` unread; `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` removes the built-in telemetry plugin. **`CLAUDE_CODE_TMPDIR` does not move the inbox socket**: it is always `/tmp/cc-socks-<uid>/<pid>.sock`, so under the `agent` profile that directory must be writable (Task 14) or `--restricted` used (no socket); whether a refused bind stops the CLI is Step 5. So the run does not end at `queued_turn_count == 0`: the session remembers whether it wrote a user line after the current turn started; at a `result` the run ends only if it did not. *Assumption, untested:* lines queued during one turn always merge into one next turn (more than two lines, staggered arrival, a line arriving as the queued turn starts); until a later run confirms it, the session keeps the run open while any written line has not been followed by a `result` that started after it, and `fake-claude` merges as observed. ### Windows
