# Sub-project 6D: Layers — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Each task names a **model tier** for its implementer: `opus` for semantics (the compositor's alpha and blend maths, effect, blur, mask and LUT definitions shared by two compositors, the plan contract and the model bump, new op kinds with inverses and footprints, glyph shaping and rasterisation, native C++ builds, job kinds with failure modes), `sonnet` for plumbing (gates, tracker, kinds that copy an existing pattern, CLI verbs, e2e wiring, docs). **Every task is test-first: write the failing tests, run them and see them fail for the stated reason, then implement.**

**Goal:** Finisher draws every layer the plan describes. After 6D:
- **effects** (`colorAdjust`, `lut`, `blur`) render in both compositors (GPU and the CPU reference), in the layer's source space, before crop and mask (spec §5.1 steps 3–5);
- **adjustment layers** apply their effects to the composite below them, mixed by their opacity (§5.1 step 7);
- **nested items** render as group layers: their timeline's layers into an offscreen, transparent target at the nested resolution, then placed like any source; and `item.insert` accepts them (4C Decision 48);
- **masks** take alpha from a **`matte` asset** read at the masked layer's source time by the nearest-frame rule, with `choke`, `feather` and `invert` (§11.3); `mask.set` and `mask.remove` are new ops; `media.matteEncode` encodes a producer's alpha frames into a `matte` asset;
- **images** (PNG, JPEG, WebP with EXIF orientation and sRGB/Display P3 profiles), **SVG** (sanitised at add, rasterised by `resvg` at the layer's pixel size) and **Lottie templates** (native thorvg, slots, text slots by `fin-captions`, `media.templateCheck`) render;
- **captions** are rasterised by a new pure crate `fin-captions` over a glyph-level `fin-text::shape`, with the plan growth of §4.3 (`CaptionPlan.paint`, caption animation presets resolved per word into `WordPlan`);
- the **`fit`** item parameter (contain, cover, none) chooses the base box (§4.3, owner decision 4);
- `fin look` shows all of it, and reports by item and code only what it truly cannot draw.

**Determinism** (spec §13.2, §13.4)
- The CPU reference stays the oracle: **every new stage is implemented twice** (WGSL and `reference/`) from **one Rust definition of what is sampled and with which weights** (kernel taps, LUT cell and fraction, choke radius, group size, raster size), passed to the shader as uniforms; the GPU result is compared with the reference **within T1** on lavapipe in CI (and Metal, D3D12, WARP in validation). No golden image is committed; T0 BLAKE3 hashes of the reference's output are.
- The reference's new modules and `fin-captions` follow the render float rules (`scripts/check-eval-floats.mjs`: `libm::` for transcendentals, scalar `f32`, fixed order, no `mul_add`, no SIMD); Task 1 adds their paths to the gate.
- **Rasters that feed both compositors are inputs, not outputs:** an image decode, an SVG raster, a Lottie frame and a caption bitmap are made once per layer and handed to both compositors as a premultiplied RGBA `Picture`, exactly as decoded video is. T0 hashes cover the raster on its own **across architectures** for captions, PNG and WebP (scalar pure Rust); **SVG and JPEG rasters are hashed per architecture, informational only** (their dependencies' SIMD paths, Decision 25), and thorvg is **T1 only** (C++; native only). The compositors' T1 is unaffected, since a raster is an input to both.
- No NaN on the hashed path: every un-premultiply is `a > 0 ? c / a : 0` with an explicit branch (spec §5.1), in WGSL and Rust.
- **`RENDER_VERSION`** moves to integration's value + 1 once, in Task 2 (6D changes what existing plans with effects, masks, nested items, images, SVG, Lottie or captions render to); intermediate 6D changes are unreleased and re-bless under that one number. A test fails when a T0 hash moves without the bump (existing rule).

## Decisions taken here

1. **Scope and boundaries.** 6D renders; it does not export. Where the spec says "export refuses" (`MATTE_MISSING`, `CAPTIONS_UNMEASURED`, `LAYER_UNAVAILABLE`), 6D produces the per-layer skip with that code in `fin look`'s result and leaves the refusal to 6E's preflight, which reads the same skips. Preview (6F) gets the same stage definitions; 6D proves the pure crates (`fin-captions`, `fin-graphics::{image,svg}`) build and hash the same on `wasm32-wasip1` and builds nothing for the browser.
2. **The model changes, once** (spec §4.4; Owner question 1): one `SCHEMA_VERSION` bump at integration's value + 1 when Task 4 lands, carrying `AssetKind::Matte`, `Mask.matte` as a `matte` asset id, the `fit` item parameter, `CaptionStyle.animation`, and the new op kinds (`mask.set`, `mask.remove`, `nested` inserts). **`Project.plugins` is not in it:** the owner's "bump per change" rule (2026-11-09) and the project rule "next free number at landing" make 8H's pins their own bump when 8H lands; the spec's "one bump shared with 8" text is amended by Task 27 (the spec allowed "whichever lands first"; this plan keeps the two independent so neither waits). Upgrade steps are identity (`snapshot_v<N-1>`, `record_v<N-1>`): every old value is a valid new value; an old free-string `Mask.matte` that names no `matte` asset stays as is and renders `MATTE_MISSING` until relinked (spec §4.4). DB: a version-only migration at `DB_VERSION` + 1.
3. **Pictures.** `fin_compositor::Picture` is either `Yuv(SourceFrame)` (6A's decoded video) or `Rgba {size, data: &[u8] /* premultiplied RGBA8, row-major, tight */, colour: RgbaColour (Rec709Encoded | DisplayP3Encoded)}`. Images, SVG, Lottie and captions produce `Rgba`. Nested groups are **not** a `Picture` a provider returns: the compositors make them internally (a GPU `rgba16float` group target; a premultiplied `Vec<[f32; 4]>` in the reference) and feed them to the same layer pass through an internal `Placed::Group` input (Decision 11). **The raster ladder** (SVG and Lottie raster sizes, Decision 13) is one function in `fin-media` (`fin_media::raster::ladder_size(intrinsic: Size, scale: f64, max: u32) -> Size`: `n = ⌈libm::log(scale)/libm::log(1.1)⌉` for `scale > 0`, `size = ⌈intrinsic × 1.1ⁿ⌉` per axis, each ≥ 1 and ≤ `max`), used by `fin-graphics` and the worker, since `fin-graphics` does not link `fin-compositor`. Ingest of `Rgba`: un-premultiply (guarded), Display P3 → Rec.709 through `fin_media::colour` (the same matrix and edge-only compression as video, spec §10.1), re-premultiply; mip levels average **premultiplied** RGBA by the exact 2×2 box (spec §5.1), so transparent texels never darken an edge.
4. **Premultiplied RGBA accumulation.** Both compositors accumulate premultiplied RGBA. The top-level frame starts **opaque black** (`[0, 0, 0, 1]`), a group starts **transparent** (`[0, 0, 0, 0]`). Each layer composites with the W3C general formula on straight source colour `Cs`, source alpha `αs = coverage × opacity × α_picture`, backdrop straight colour `Cb` and alpha `αb`: `co = αs·(1 − αb)·Cs + αs·αb·B(Cb, Cs) + (1 − αs)·αb·Cb`, `αo = αs + αb·(1 − αs)`, with each blend mode's `B` as today. **`add` is special-cased** as today (`reference/blend.rs:26`: `dst + a·cs`): premultiplied `co = αs·Cs + cb_p`, `αo = αs + αb·(1 − αs)`, never through `B = cb + cs` (which rounds differently in `f32`). **When `αb = 1` the reference takes 6A's exact operation order** for every mode (a branch on the backdrop being opaque, not the general formula with `αb = 1` substituted, which would round differently), so **every existing T0 hash is unchanged** (a test asserts it before `RENDER_VERSION` moves). GPU blend states: colour as today (`normal` `One, OneMinusSrcAlpha`; `screen` `One, OneMinusSrc`; `add` `One, One`); **alpha** changes from 6A's `Zero, One` ("the frame is opaque", `blend.rs:46`) to **`One, OneMinusSrcAlpha` for every fused mode, `add` included** (so a group's alpha is `αs + αb(1 − αs)`, never `αs + αb`); with an opaque frame the alpha result is 1 either way. The shader modes (`multiply`, `overlay`, `darken`, `lighten`) compute the general formula in `blend.wgsl` with the backdrop's alpha read from the ping-pong target. Transitions mix premultiplied values by `curve(progress)` (`crossfade` encoded, `dissolve` linear light on un-premultiplied colour, then re-premultiplied by the mixed alpha).
5. **Where effects and masks run: the layer's source space** (spec §5.1 steps 3–5, in that order). A layer with effects or a mask is processed in a scratch target the size of its ingested picture (at mip level `⌊L⌋` when `L ≥ 1`, so a 4K source on a 1080p output is processed at 1080-ish, not 4K), then sampled by the normal layer pass (crop, coverage, transform, opacity, blend). **Lengths given in pixels (`blur.radius`, `mask.choke`, `mask.feather`) are timeline pixels** (spec §11.3) and are converted per axis to the processed picture's pixels with the layer's placement scale: `r_x = r / s_x`, `r_y = r / s_y`, where `s_x`, `s_y` are output pixels per processed pixel along the picture's axes divided by `out / timeline` (computed in Rust in `placement`, shared). So a blur looks the same at any output size and any source resolution; under non-uniform scale it is anisotropic in source space and round on screen, as editors do. Outside the picture, samples clamp to its edge (editors' "repeat edge pixels"). **How a processed picture is sampled:** the processed picture `P` (at level `ℓ = ⌊L⌋`, made from the ingested picture's box chain, Decision 3) gets its own box chain, and the layer pass samples it with the explicit-level rule at `L − ℓ` (levels `0` and `1` of `P`'s chain blended by the fraction), so geometry, coverage and sampling are 6A's exactly; with an empty chain nothing changes (6A's path, bit-exact). Non-linear stages (`colorAdjust`, `lut`, the matte's choke) run at level `ℓ`, not full resolution: results differ from a full-resolution application by the mip averaging, accepted because the output is itself at that scale (editors process at preview resolution the same way), and the reference does the same thing, so T1 compares like with like. **Effect ABI** (pl §10.4): only `colorAdjust` is a pure `fn effect(uv, src) -> vec4f` with a uniform block; `lut` (a 3D texture) and `blur` (multi-tap, two passes) are built-in stages outside that ABI, as is the matte stage.
6. **`colorAdjust`** (one definition in `stages/colour_adjust.rs`, uniforms generated from its `ParamSpec`s, pl §10.4's ABI): on straight colour `c` (display-encoded Rec.709), `lin = bt1886_to_linear(c)` (γ 2.4), then in linear light: **exposure** `lin × 2^exposure`; **temperature** and **tint** as white-balance gains `r × (1 + 0.1·temperature + 0.05·tint)`, `g × (1 − 0.1·tint)`, `b × (1 − 0.1·temperature + 0.05·tint)`; **saturation** about Rec.709 luminance `Y = 0.2126 r + 0.7152 g + 0.0722 b`: `Y + (c − Y)·saturation`; negative values clamp to 0; re-encode (`linear_to_bt1886`, values above 1 kept for the next stage); **contrast** in encoded space about mid-grey: `(c − 0.5)·(1 + contrast) + 0.5`; alpha unchanged. The 4C defaults leave every pixel bit-identical (a test on the reference: identity in, identity out, exactly).
7. **`lut`** (spec §10.1): the `.cube` parser lives in `fin-compositor::lut_cube` (pure; fuzzed): `TITLE`, `LUT_3D_SIZE` 2…65, `DOMAIN_MIN`/`DOMAIN_MAX`, comments and blank lines; `LUT_1D_SIZE` is `LUT_INVALID {reason: oneDimensional}`; values must be finite; row count exact. The LUT applies to straight display-encoded colour, the input mapped from the domain to `[0, size − 1]` and clamped, **trilinear by explicit `textureLoad` of the 8 corners** (no hardware filtering, whose weight precision varies between GPUs), mixed with the input by `intensity`. The texture is `rgba16float` 3D; the reference rounds its table through `f16` the same way, so the two read the same values. The LUT file is the `lut` asset's `original` from the manifest, parsed by the worker (cached by fingerprint in the warm worker); a parse failure is the layer's `LUT_INVALID {line, reason}` skip.
8. **`blur`**: a separable Gaussian, `σ = radius / 3` in timeline pixels (so `radius` is the kernel's visible reach, ±3σ, as editors' "radius" sliders behave), converted to processed pixels per Decision 5. Taps: half-width `⌈3σ⌉` per axis, weights `exp(−x²/2σ²)` in `f64` (`libm`), normalised to sum 1, passed as `f32` uniforms; a half-width above 64 taps is processed on a downsampled copy (the box mip of Decision 3 at level `k = ⌈log2(half/64)⌉`, σ divided by `2^k`) and sampled back bilinearly by the layer pass. On premultiplied values (so edges do not darken). `radius = 0` is a pass-through, bit-exact.
9. **Masks** (spec §11.3): the matte is the `matte` asset named by `MaskPlan.matte`, decoded like any source (`Sources`, the same `OpenCache`, the same nearest-frame `frame_at` on the matte's own table) at **the matte time**, defined per layer kind and documented in `fin-core` (`MaskPlan` doc, spec §4.3): **`clip`: `source.time`** (mattes are produced one frame per source frame, so a speed change follows the source); **`image`, `caption`, `graphic`, `nested`, `adjustment`: `local`** (an image's `source.time` is always 0 and a graphic's is its template time, `eval/source.rs:41`, neither of which a producer's frames follow). Task 16 adds `MaskPlan.time: Rational` (the resolved matte time, filled by eval), so the engine reads it from the plan rather than choosing; a plan field added on purpose, corpus re-blessed for masked projects. **Orientation:** a matte is in its own file's **display orientation** (a producer receives display-oriented frames, pl §10.3; a matte file's own rotation tag is applied), and is mapped onto the masked picture's display box; since processed pictures are in coded orientation (rotation and pixel aspect are applied by the layer matrix, `placement.rs:39-59`), the matte stage samples the matte through the inverse of the source's rotation and pixel-aspect mapping (one Rust function shared by both compositors). Alpha is its **range-expanded luma** (`(Y − 16)/219` for limited range, clamped 0…1); the matte is sampled stretched to the processed picture's size (producers emit `maxSide` frames, pl §10.3); then **choke** (a separable min filter of radius `choke` timeline px converted per Decision 5, rounded to whole processed pixels), **feather** (Decision 8's Gaussian with `σ = feather / 3`), **invert**, and the result multiplies the picture's alpha (and its premultiplied colour) after effects and before the layer pass applies crop and coverage. **Deviation (recorded by Task 27):** spec §11.3 multiplies "after crop and edge coverage"; because crop and coverage are multiplicative and independent of the matte, the product is the same per pixel except for where bilinear sampling straddles the crop edge (sub-pixel), so 6D applies the matte in source space as the last stage, where it is sampled once with the picture instead of a second time in output space. A missing or unreadable matte: the layer is drawn **unmasked** and skipped with `MATTE_MISSING {item, matte}` (spec §11.3: preview draws, export refuses). A matte whose asset kind is not `matte` (an old free string) is `MATTE_MISSING {reason: notAMatte}`.
10. **Adjustment layers** (spec §5.1 step 7): their effects run on a copy of the accumulation below them (in output pixels; lengths scaled by `out / timeline`), and the result is mixed with the unadjusted composite by the layer's `opacity` (and a transition's weight) in display-encoded premultiplied values. Their transform and crop are defaults (eval guarantees it); **their mask** (Owner question 8) applies in frame space: the matte is contain-fitted to the frame (`base_box(matte display, frame)`) and multiplies the mix weight. Inside a nested group, an adjustment layer adjusts only the group's layers below it.
11. **Nested groups** (spec §5.1 step 1): the children are rendered by the same walk into a transparent group target of size `⌈nested resolution × k⌉` (each axis ≥ 1, ≤ the GPU limit), `k = out.width / plan.resolution.width` (the output's scale; so a nested 1080p timeline in a 1080p frame rendered at 540p output is drawn at 540p, not 1080p); the group is then a premultiplied `Picture` whose display size is the nested resolution, placed by the item's `fit`, transform, crop, effects, mask, opacity and blend. Depth is eval's (`MAX_NESTING` 16); the compositors recurse with an explicit stack of group targets drawn from the texture pool. `nested` inserts (4C Decision 48): `item.insert {kind: nested, timeline, sourceIn}` on a video track; refused with `NESTED_CYCLE` when the target timeline is the item's own timeline or (transitively) contains it, `NOT_FOUND` for an unknown timeline; `timeline.remove` of a timeline a nested item uses is already refused with `TIMELINE_NESTED` (`ops/timeline_remove.rs:47`); Task 6 adds tests only.
12. **Images** (spec §11.2): `fin-graphics::image::decode(bytes, limits) -> Result<DecodedImage {size, rgba8_premultiplied, colour, orientationApplied, warnings}, CoreError>` with `png` (16-bit reduced to 8 by rounding; palette and grey expanded; APNG's first frame only), `zune-jpeg` (baseline and progressive; CMYK refused `UNSUPPORTED_PIXEL_FORMAT`), `image-webp` (lossy, lossless, alpha; animated: first frame). **EXIF orientation** (JPEG `APP1`, PNG `eXIf`, WebP `EXIF`) via `kamadak-exif`, applied to the pixels (all eight orientations). **ICC profiles** are classified, not interpreted: a tiny own parser reads the `rXYZ`/`gXYZ`/`bXYZ`/`wtpt` tags and the `TRC` kind; primaries within 0.002 of sRGB → sRGB; of Display P3 → `DisplayP3Encoded` (converted at ingest, Decision 3); anything else is treated as sRGB with the warning `COLOUR_PROFILE_UNSUPPORTED` in the layer's notes (a `LookSkipped` with `drawn: true`). Limits: pixel count ≤ `MAX_DIMENSION²` from `fin-probe` and ≤ 64 Mpx, decoded bytes ≤ 256 MiB (`MEDIA_LIMIT {limit: imagePixels}`). Decoded images are cached in the warm worker by (fingerprint) with an LRU bound of 512 MiB.
13. **SVG** (spec §11.2; Owner question 5): **sanitising at add** lives in `fin-probe::svg` (in-process in `fin-node`, safe Rust, inside the existing panic guard): a `usvg` parse with a refusing resolver (no `href` outside `data:image/{png,jpeg,webp}`, no external CSS), plus a pre-pass over `roxmltree` that refuses `<script>`, `foreignObject`, `on*` attributes, `<!ENTITY` (already), more than 1,000,000 nodes or nesting deeper than 256, and `<image>` data above 16 MiB or of a type other than PNG, JPEG or WebP: `SVG_UNSAFE {reason}`; allowed embedded images decode through resvg's pure-Rust `raster-images` decoders (tech table), with the same pixel limit as Decision 12; parse errors `SVG_INVALID {reason}`. The probe reports the font families `<text>` uses (`svg.fonts`, probe-only, never stored), and `asset.probe` with a `projectId` refuses an SVG whose families are not all pinned (`FONT_UNPINNED`, the existing code and fix). **The worker re-runs the same sanitiser** (`fin_probe::svg::sanitise`, the one function) before rasterising, because a file can change after add (the fingerprint check catches content changes; the re-run is defence in depth). **Raster**: `resvg` 0.49 on `tiny-skia` at the layer's pixel size, with a `fontdb` holding **only the project's pinned fonts** (from the worker's `FontCache`; no system fonts are ever loaded); the raster size is the base box × scale × `out / timeline`, **quantised up to the ladder `1.1^n`** (so a re-raster happens only when the effective scale changes by more than 10 %, spec §11.2, and the size is a pure function of the plan, the same for both compositors); cached in the warm worker by (fingerprint, raster size).
14. **The "sanitised tree is a cache entry" (spec §11.2) is not built:** the worker parses the SVG each time its raster is not cached (parse costs milliseconds at these sizes, the raster is what is cached). Recorded as a deviation by Task 27.
15. **Lottie through native thorvg** (spec §11.1, arch §27.10): `fin-thorvg-sys` builds thorvg from the submodule `third_party/thorvg` with `cc` as C++17 (no meson), compiling only `src/common`, `src/renderer` (with `sw_engine`), `src/loaders/{lottie (with its vendored rapidjson, MIT),raw,png (lodepng),jpg (jpgd)}` and `src/bindings/capi`; **`THORVG_LOTTIE_EXPRESSIONS_SUPPORT` undefined** (expressions bring JerryScript, a JavaScript engine running on untrusted templates; templates using expressions render their static values; Task 22 confirms the define name at the pinned tag); SIMD off (`THORVG_AVX_VECTOR_SUPPORT` and NEON undefined), threads off (thorvg's task scheduler with 0 threads), `-ffp-contract=off`, exceptions and RTTI as thorvg requires; `build.rs` refuses any other thorvg version until the source list is re-checked (as `fin-dav1d-sys` does). **The version is the thorvg inside the dotlottie-web release 6F will pin** (arch §27.10: a pixel-identical pair was measured at thorvg v1.1.1 / dotlottie-web 0.81.0); Task 22 reads dotlottie-web's (via dotlottie-rs's) thorvg pin for the newest release that is ≥ 7 days old (0.82.1, 2026-11-02, at planning time) and pins that tag; T2 against dotlottie-web is 6F's (it needs the browser build). A C shim (`csrc/tvg_shim.c`, ours) owns every thorvg handle; Rust sees `load(json bytes) → Animation`, `frame_count`, `duration`, `set_slots(json)`, `render(frame, w, h) → premultiplied RGBA8` (thorvg's `ABGR8888S` straight output is converted, or `ARGB8888` premultiplied read per byte order, whichever the pinned version offers; Task 22 tests both channel orders against a known red/green/blue/alpha frame).
16. **Lottie frames and slots**: the frame drawn is `round_half_even(GraphicPlan.time × fr)` clamped to `[ip, op − 1]` (the template time is rational, `fr` from the probe); slots: colour (`[r, g, b, a]` → Lottie `[r, g, b]` and opacity), number, vec2, text and image slots are applied as thorvg slot JSON (`tvg_lottie_animation_gen_slot`/`apply_slot`); **text slots are laid out by `fin-text` and rasterised by `fin-captions`** at the slot's box size oversampled ×2 (arch §27.10, spec §11.1) and injected as **image slots** (a `data:image/png;base64,` asset written by the worker's `png` encoder); thorvg's text engine is never used. Fonts a template names must be pinned (`FONT_UNPINNED` at add, through `asset.probe` as for SVG). The raster size follows Decision 13's ladder; frames are cached per (fingerprint, slots hash, frame, size) in the warm worker with an LRU bound.
17. **`media.templateCheck`** (spec §3.3, §11.1): a **cold** kind on `worker:media` (`normal`, pool `cpu`, timeout 15 s; a cold spawn runs one job and exits, `kinds.ts:270`, which is the throwaway worker spec §11.1 asks for): it renders the template's first, middle and last frames and one frame with every slot at a non-default value, at 256 px on the longer side; success answers `{frames: 4, millis}`; a crash (`WORKER_CRASHED`), hang (`WORKER_HUNG`/timeout) or thorvg load failure becomes `TEMPLATE_INVALID {asset?, reason: crashed|hung|loadFailed|slots}`. **Where it gates** (Owner question 9): `asset.probe` for a `lottieTemplate` submits it and waits (it runs in about a second), and the verdict is cached in `finisherd` by (fingerprint, `RENDER_VERSION`, thorvg version) so a re-add is instant; a client that commits `asset.add` without probing is not refused, and a template that later crashes a render fails only that job (5C's retries and poison handling).
18. **Captions raster** (spec §11.4): `fin-text::Measurer::shape(request) -> ShapedText {words: [ShapedWord {glyphs: [Glyph {face, id, x, y}], box}]}` over **the same code path as `measure`** (one internal function returns both; `measure` keeps its signature and output bit-for-bit, a test asserts it over the 4C caption corpus); `fin-captions::raster(plan: &CaptionPlan, shaped: &ShapedText, fonts: &dyn FontBytes, scale) -> CaptionRaster {size, origin, rgba8_premultiplied}` draws, in order, the **background box** (rounded rectangle of `padding` and `radius`, around each line's ink box per `CaptionStyle.background`), the **stroke** (zeno stroke of the glyph outline at `stroke.width` frame px, round joins, drawn under the fill), the **fill** (the word's colour: `paint.color`, or `paint.highlight` for active words, or the animation's colour), with swash's scaler (hinting off, `libm`), 8-bit coverage accumulated in `f32` in a fixed order; the renderer compares each word box from its own shaping with the plan's layout and fails the job with `PLAN_MISMATCH {at, reason: glyphs}` on any difference. Bitmaps are cached by (layout hash, paint hash, animation state hash, scale) in the warm worker. A caption without a layout (`unmeasured`) is not drawn and is skipped `CAPTIONS_UNMEASURED {items, keys}` (fix: `fin fonts fetch`).
19. **Caption plan growth** (spec §4.3; Owner question 3): `CaptionPlan.paint: CaptionPaint {color: [f64; 4], stroke?: {color, width}, background?: {color, padding, radius}, highlight?: [f64; 4], origin: [f64; 2]}` — colours resolved from the style and the block's overrides to sRGB 0…1 (plan 4C Decision 12), the **origin** the layout's top-left in frame pixels from `position` and the safe zone (the rule the measurer already uses to wrap, written down once in `eval/caption_paint.rs` and shared with `captions::measure_caption`); `WordPlan` gains `scale: f64` (default 1), `offset: [f64; 2]` (frame px, default 0), `opacity: f64` (default 1), `color?: [f64; 4]` (absent = `paint.color`), each skipped at its default so plans without animation keep their bytes except for `paint`. **Presets** (`CaptionStyle.animation: none|pop|karaoke|fade|slideUp`, absent = `none`), with `u` the time since the word's `start`: `pop`: the active word's `scale = 1 + 0.15·sin(π·min(u / 0.15 s, 1))` (a 150 ms bump), others 1; `karaoke`: words with `start ≤ local` take `highlight` (or `color` when no highlight), later words `color` with `opacity 0.6`; `fade`: `opacity = clamp(u / 0.12 s, 0, 1)` for each word (0 before it is spoken); `slideUp`: every word `offset = [0, (1 − e)·0.5·lineHeight·size]`, `opacity = e`, `e = smoothstep(clamp(local / 0.2 s, 0, 1))` (the block rises in over its first 200 ms). All in exact rationals where times compare, `f64` with `libm` for the curves. `scale` animations are drawn as per-word quads rasterised ×2 (spec §11.4); offsets and opacity are applied while the block bitmap is built.
20. **Colour emoji** (spec §11.4; Owner question 6): CBDT bitmap glyphs from the catalog's Noto Color Emoji bitmap build (OFL-1.1, already the catalog's licence class), scaled with the box mip chain to the glyph's size and drawn in the fill pass; COLRv1 stays a later follow-up. If the catalog does not yet carry the bitmap build, Task 21 adds the catalog entry (`fin-fonts`' catalog licence gate applies).
21. **`fit`** (spec §4.3, owner decision 4): an item parameter `fit: contain|cover|none` (enum, not animatable, on `clip`, `image`, `graphic` and `nested` items; absent = `contain`) in the item param registry; `Layer.fit` (skipped when `contain`, so existing plan hashes keep their bytes); `geometry::base_box(display, frame, fit)`: `contain` as today, `cover` with `max` instead of `min`, `none` at 1 display px = 1 frame px, centred. Crop fractions stay fractions of the base box.
22. **Matte assets** (spec §11.3, pl §10.3; Owner question 4): `AssetKind::Matte` carries the media fields (`video` info) and is added two ways: (1) **`fin asset add --matte <file>`** (`asset.probe {as: matte}`): a video file with one video track (any decodable codec; audio ignored) becomes a `matte` asset, copied into `assets/` write-once like any added file; (2) **`media.matteEncode`** (cold, `normal`, pools `gpu`, `hwenc`): params `{projectId, source: asset id, frames: count, width, height}`, input **chunk files** `in/alpha-NNNNNN.bin` of `gray8` frames (at most 64 frames each, a 32-byte header `FINALPH1 {width, height, first, count}`, each chunk ≤ 256 MiB, the total frame count ≤ the source's), written by the **host** with `fin-shm::write_input` from a producer's output after the producer exited (spec §3.4: the host never maps a file a less-trusted process can still write; it copies validated chunks into the matte job's `in/`). Streaming a producer live through a ring is sub-project 8's (8C) and not needed here. The worker reads the chunks one at a time (memory bounded by one chunk). The source's sample table comes in `in/table.bin` written by `prepare` from the source's `MediaInfo`, following `fin-node/src/media/asset_job.rs`'s pattern for asset jobs. Output `out/matte.mp4` encoded at that sample table (one frame per source frame, the source's `pts` and durations) with **SVT-AV1** (8-bit 4:2:0, luma = alpha in **full range** with `colr` tagged full, chroma 128; preset 6, CRF 12: "high quality"; spec §11.3's export encoder policy, `EncodePurpose::Matte`) on every OS in 6D; H.264 4:0:0 through VideoToolbox and Media Foundation (spec §11.3 "where an `os` encoder offers it") is recorded for the macOS/Windows hosts after 6B-1 Tasks 4–8 and not built blind. The host's `onSucceeded` moves the file into the project's `assets/` and commits an `asset.add` of kind `matte`. In 6D only a **test-hooks producer** (`media.testMatteProducer`, feature `test-hooks`) writes the frames (into its own `out/`, copied by the host as above); real producers are sub-project 8's.
